# E6C1 — Scoped Clearance and Emergency Safety (11 October 2026)

**Status:** local-development code and focused regression PASS; **E6 overall remains OPEN**, production approval withheld. Only EAGLT02 authorised; no VM deployment, real case classification or identity evidence upload.

## Implementation scope
- `20261011220000_operations_scoped_clearance_safety.sql` extends the existing E6B `has_operations_case_scope` lookup for `safety_investigator`, resolving the current signed-in JWT against an issued country/province/category grant, registered ISO subdivision, canonical service category and case mapping. It adds `has_operations_clearance_scope`, validating the clearance's `evidence_case_id` is owned by the very same `provider_id`; a misbound historical clearance fails closed for ordinary staff.
- The former broad-administrator policy on `vendor_clearance_revocation_events` was replaced by an investigator-scoped select policy. `list_vendor_clearance_status()` requires an active safety duty and returns only the caller's verified, in-scope provider rows. It preserves the existing limited output schema and 200-row bound; no raw KYC data or signed documents are returned.
- `revoke_vendor_activation_clearance` now requires a scoped independent investigator who is not the provider, identity reviewer or final approving officer. It locks the clearance, records the reason, revokes once, pauses all currently active provider listings, and appends an event in one transaction. An ordinary administrator without a safety grant is denied.
- `emergency_revoke_vendor_clearance_trusted` provides a narrowly separate **service-role-only** stop for unmatched/unclassified legacy clearances. It accepts an explicitly identified trusted operator and an incident reason, revokes and pauses the provider, and records a prefixed audit reason atomically. It cannot be executed by `authenticated` or `anon`. Operational procedure, second approval for nonemergency use and secret custody are not established; **do not expose this endpoint in a client or browser**.
- To prevent a premature release, the legacy `admin_set_provider_service_status(uuid,text)` blocks `active` unconditionally, and permits only an in-scope, case/category-verified safety pause. Other changes are denied. Legacy `review_provider_application` is sealed with an explicit permission error until a case-linked review workflow is established. Existing `pause_expired_vendor_clearances()` remains service-only.
- Operations UI: authenticated non-admin staff with active safety duty can access an isolated `Safety clearances` tab without full administrator shell permissions; existing policy/case duties retain their own tabs. The clearance view supports an explicit read-only presentation; its refresh callback was corrected to avoid returning a Future from `setState`. No standalone browser sign-in/role acceptance has occurred.
